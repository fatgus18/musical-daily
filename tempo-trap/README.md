# Tempo Trap

A complete daily BPM guessing game for Musical Daily, built as an independent Next.js application. It uses real English-language recordings by The Weeknd, Dua Lipa, Harry Styles, Taylor Swift, Billie Eilish, and other artists, with their actual artwork and Spotify song links.

## Run

Requires Node 22.18+ and npm.

```sh
npm install
npm run dev
```

Open <http://localhost:3002>. The Musical Daily return link defaults to <http://localhost:3001>.

For stable sessions across development restarts, copy [.env.example](.env.example) to `.env.local` and set `TEMPO_SESSION_SECRET` to a random value of at least 32 characters. A development-only random fallback is available. Production requires the environment variable. Generate a value with:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

## Game rules

- Five rounds. The daily set is deterministic, has five distinct artists, and changes at midnight IST (Asia/Kolkata, 18:30 UTC), independent of the player’s time zone.
- Artist and album artwork appear before playback. The track title is revealed after the guess.
- Press Play to hear exactly 15 seconds. Audio is downloaded and decoded before playback; buffering never uses answer time.
- When playback finishes, BPM entry unlocks and a separate 15-second timer begins.
- Enter a whole number from 40–220. Lock it in early or let the timer submit the current valid answer. Empty or invalid answers score zero.
- Each round awards up to 1,000 points. Within 2 BPM earns 1,000; larger relative errors earn progressively fewer points. Half-time and double-time pulses within the input range count too.
- Daily progress, historical scores, streaks, and personal bests are browser-local. Practice is unlimited and separate from daily stats.
- Reloading during guessing preserves the original deadline. Reloading during playback offers the clip again. Failed submissions retain the locked answer and can be retried idempotently.

## Music pipeline

[data/catalog-releases.json](data/catalog-releases.json) selects immutable catalogs in [data/catalog-releases](data/catalog-releases). These are generated by the shared [music-catalog](../music-catalog/README.md) database and resumable import pipeline. [data/seeds.json](data/seeds.json) and [data/catalog.json](data/catalog.json) retain the original 16 reviewed records as high-priority evidence; they no longer limit the playable pool.

Playback and artwork come from Apple's public preview catalog, following the approach used by the existing Blackjack game. These are the actual recordings, **not Spotify-hosted audio**. Spotify links are checked against Spotify's oEmbed metadata. No Spotify login or API key is required.

The player uses the 15-second segment beginning 7.5 seconds into the provider's preview. The provider selects where that preview falls in the full song; the API does not expose the original recording's absolute timestamp. Playing an arbitrary exact position in a full song would require a different authorized playback source.

```sh
npm run catalog:check
npm run catalog:refresh
```

Install the shared catalog project's dependencies first. Refresh delegates to its maintenance pipeline: source-labelled English tracks with usable BPM are matched to Apple recordings by title, primary artist and duration, then preview availability is checked. Alternate versions and language-review flags are excluded from automatic publication. Every answer retains provenance and BPM quality. Refreshes publish new immutable releases for a future day; practice uses them immediately. There is no external API lookup on page load, and audio files are not stored in the repository or rehosted.

To expand the pool, run another shared enrichment batch or ingest a sourced provider export. No song count is hardcoded. Daily releases contain a rotation of five distinct artists per day without repeating recordings within that release's cycle; the cycle repeats when exhausted. Existing signed sessions keep their original catalog version. Rebuild/redeploy the app after publication. Provider-estimated BPM can still need listening review for tracks that change tempo. External previews may be withdrawn or region-restricted; failures offer a retry rather than an unrelated recording.

Spotify's [API change notice](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api) explains the restrictions on audio features for newer apps. BPM is therefore sourced explicitly in the catalog instead of relying on that endpoint.

## Application structure

- [src/hooks/use-tempo.ts](src/hooks/use-tempo.ts): playback lifecycle, phase transitions, deadlines, retry handling, and persistence.
- [src/components/tempo-game.tsx](src/components/tempo-game.tsx): game, results, stats, help, and sharing.
- [src/lib/game.ts](src/lib/game.ts): deterministic selection, scoring, and input bounds.
- [src/lib/session.ts](src/lib/session.ts): HMAC-signed progression and results. BPM answers for future rounds are never sent in the daily API response or session token.
- [src/lib/storage.ts](src/lib/storage.ts): validated local progress, historical stats, and streaks.
- [src/app/api/daily/route.ts](src/app/api/daily/route.ts): daily/practice puzzle creation.
- [src/app/api/guess/route.ts](src/app/api/guess/route.ts): validated, server-scored guesses and signed continuation tokens.

Guest games use browser storage. Signed-in daily games use the hub's shared Musical Daily account database, with account-bound signed progression and a server-owned guessing deadline. Practice remains outside daily statistics. This is a casual game, without a global competitive leaderboard; the browser still controls audio playback.

## Musical Daily accounts

Sign in with Google on this game or the hub to use the same account. Configure the hub's Google client first, following its [README](../musical-daily/README.md). Google's local authorized redirect URI is exactly `http://localhost:3001/api/auth/google/callback`; production uses `/api/auth/google/callback` on the public HTTPS hub origin. This app's callback is an internal account handoff and is not registered with Google. This app uses the sibling [account service package](../shared/accounts/), so retain it during dependency installation and deployment.

Daily progress is stored by account and IST puzzle date. Completed rounds and guessing deadlines restore on other devices. After audio ends, the server starts a 15-second deadline; repeating that request cannot restart it. Submitted answers are scored on the server, with a two-second transport allowance. A newer device's saved state wins over stale requests; the UI offers a reload instead of silently replacing it. Completion and statistics are saved atomically, and retrying a lost response returns the original saved result. Signing out stops playback and restores the separate guest space.

Guest aggregates remain on their original device and are not silently imported into an account because old client-only history cannot be revalidated. Account requests fail closed during service outages; the saved answer can be retried. Local save keys are scoped to account identity, and an old account's signed round cannot be submitted by another account.

## Production

Deploy this folder as a separate Next.js project with:

- `TEMPO_SESSION_SECRET`: a stable random value, at least 32 characters, shared across instances.
- `NEXT_PUBLIC_HUB_URL`: the deployed Musical Daily URL, set before building.
- `MUSICAL_DAILY_AUTH_ORIGIN`: the hub's origin, serving account endpoints.
- `MUSICAL_DAILY_APP_ORIGIN`: this game's origin.
- `MUSICAL_DAILY_SERVICE_SECRET`: the hub's shared server-only service secret, at least 32 characters.

```sh
npm ci
npm run build
npm start
```

On Vercel choose `tempo-trap` as the root directory. Configure the hub's `NEXT_PUBLIC_TEMPO_TRAP_URL` with this app's public URL. Secrets remain server-side. Keep the deployed catalog consistent across instances. Rotating the session secret expires unfinished sessions.

### Daily rollover

The daily API, puzzle number, countdown, guest streak and account streak use the same IST calendar day. New-day checks run while the page is open and when it regains focus. An untouched mix or one already completed before midnight refreshes automatically. Listening, guessing, and partly played mixes keep their original signed session and deadline, with a visible button to switch after the current round. Finishing an in-progress mix after midnight keeps its results and share button on screen until the player chooses the new daily mix. Practice is never interrupted. Saved entries and results retain their original date keys, including entries from before the UTC-to-IST change; there is no renaming, deletion, or new seed for an already published calendar date. An open previous-day mix can still finish while its signed session remains valid (48 hours from creation). Catalog effective dates now refer to the IST daily date for Tempo.
